# issue-breakdown：拆需求

## 执行边界

先遵循 Plane 团队规范。没有可用 Plane MCP 时只草拟，不宣称读取或写入成功。调用参数以当前工具 schema 为准。

先调用 `workspace(action="list")` 定位目标；歧义时询问。除该发现调用外，每次读取、分页、写入及核验都显式传 `workspace_slug`，同时携带目标项目和对象标识。跨工作区分别查询、分别分页并标明 slug 与项目来源；不得使用历史默认工作区，不得在无权限时切换工作区重试同名对象。

列表按返回的 cursor、next_page 或 has_more 连续分页，直到结束；如果达到客户端预算、权限受限或某页失败，明确标注仅覆盖已读取范围，不把部分数据当作全量排名、计数或规划依据。不要猜测分页参数。

写入前展示具体目标与变更，获得用户明确确认；已有明确授权仅在原范围内沿用。沉默、空消息或回车不算确认。任何步骤失败立即停止依赖它的后续操作，报告已成功、失败和未执行部分；结果不明时先读取核验，避免重复创建。写后读取核验，只报告已证实的结果。

## 1. 输入

需求可能来自：

- 用户直接给的文字
- Plane 页面：`page` 工具 `action="get", workspace_slug="<目标 slug>"`
- 已有工作项：`workitem` 工具 `action="get", workspace_slug="<目标 slug>"`（拆成它的子工作项）

确定目标项目；不明确就问。用 `project` 工具 `action="labels", workspace_slug="<目标 slug>"` 和 `action="states", workspace_slug="<目标 slug>"` 了解可用的标签和状态。

## 2. 拆分方案（先不创建）

按 Plane 团队规范 的规范拟定：

- 一个父工作项（输入已是工作项时就用它）
- 3–10 个子工作项，每个半天到三天的工作量，能独立验收；每个写标题、一句话描述、建议优先级、建议标签

用表格展示，问：「按这个创建？可以增删改」。

## 3. 创建

确认后：

1. 需要时创建父工作项：`workitem` 工具 `action="create", workspace_slug="<目标 slug>"`，描述里写完整背景与验收标准。
2. 逐个创建子工作项，传 `parent=<父编号>`。
3. 如果用户要求，把它们加入周期（`cycle` 工具 `action="add_items", workspace_slug="<目标 slug>"`）或模块。

任何一步失败就停下，报告已创建的部分，不要重试到底。

## 4. 汇报

列出创建的编号与标题，以及父工作项编号。

“理由”一句话，每条不要重复同一句话。

## 1. 确定周期

`cycle` 工具 `action="list", workspace_slug="<目标 slug>"`。没指定周期时，选当前日期落在 start_date 与 end_date 之间的周期；没有则选最近一个未开始的周期。都没有就问用户是否新建（`cycle` 工具 `action="create", workspace_slug="<目标 slug>"`，需要名称、开始和结束日期）。

`workitem` 工具 `action="list", workspace_slug="<目标 slug>"`，项目内、`filters={"state_group__in":"backlog,unstarted"}`，按 `priority` 排序，取前 30 个，排除已在该周期的。

按优先级分组展示，每行：编号、优先级、标题、负责人（没有写“未分配”）、截止日期。

## 4. 确认后加入

请用户给出要加入的编号（或「全部 high 以上」这样的描述，先展开成具体编号再确认）。确认后调用 `cycle` 工具 `action="add_items", workspace_slug="<目标 slug>"`，`work_items` 传编号列表。

## 5. 汇报

「已向 <周期名> 加入 N 个工作项，周期内现有 M 个」，并提醒仍未分配负责人的工作项。

# issue-ship：提交 PR 并更新 Plane

## 执行边界

先遵循 Plane 团队规范。没有可用 Plane MCP 时只草拟，不宣称读取或写入成功。调用参数以当前工具 schema 为准。

## 1. 找到工作项

先检查 shell/Git、远程推送和 PR 工具是否可用以及授权范围。缺少工具时仅提供待执行步骤；没有真实 PR URL 时停止，不能写“已提交 PR”评论或更新为评审中。

从 `git branch --show-current` 中以忽略大小写方式匹配 `[A-Z0-9]+-[0-9]+`，再将编号转为大写（如 `fix/WEB-12-safari-login` → `WEB-12`）。匹配不到就问用户编号。用 Plane MCP `workitem` 工具 `action="get", workspace_slug="<目标 slug>"` 读取。

## 2. 检查

- `git status`：有未提交改动就先问用户是否提交（不要擅自提交）。
- 对照工作项描述里的待办条目，列出哪些看起来还没完成，询问是否仍要提交。

## 3. 推送并创建 PR

1. 明确确认目标分支、远程和推送/创建 PR 的范围，重新检查当前分支后执行 `git push -u origin HEAD`；失败立即停止。
2. 使用当前客户端可用的 PR 创建工具；有 shell 且已安装并认证 gh 时可用 `gh pr create`。先检查是否已有该分支的 PR，避免重复。PR 标题以 `[WEB-12]` 开头，正文第一行写 Plane 工作项链接或编号。
3. 记下 PR 地址。

## 4. 更新 Plane

1. `workitem` 工具 `action="add_comment", workspace_slug="<目标 slug>"`：「已提交 PR：<地址>」，再加两三条改动要点（Markdown 列表）。
2. 用 `project` 工具 `action="states", workspace_slug="<目标 slug>"` 查看状态：有名称含 Review / 评审 的状态就改成它；没有就保持当前状态，**不要**改为完成——合并后才算完成。

## 5. 汇报

「WEB-12 已提交 PR <地址>，Plane 已评论，状态：<状态>」。

# Plane 团队规范

在通过 Plane MCP 创建或修改任何内容时遵循以下规范。如果项目有明确的团队规范，优先遵循该规范。

## 执行边界

先遵循 Plane 团队规范。没有可用 Plane MCP 时只草拟，不宣称读取或写入成功。调用参数以当前工具 schema 为准。

## 工作区定位与权限

- 先调用 `workspace(action="list")` 列出当前令牌可访问的工作区，按用户的名称、slug 或链接自动定位；有歧义时询问。跨工作区查询分别调用、分别分页，并标明工作区名称/slug 与项目来源。
- 定位后每次工具调用显式传 `workspace_slug`（含读取、搜索、分页、写入及核验），避免同名项目与重复工作项编号串区。各流程示例中的 `<目标 slug>` 必须替换为已定位的工作区 slug。
- `workspace(action="list")` 无需 slug；其他工作区操作必须显式提供 `workspace_slug`。缺失时先 list 定位，仍不明确则询问，不使用请求头或历史工作区默认值。个人 token 可跨有权限的工作区，workspace-scoped token 不得超出绑定工作区；每次调用仍校验成员资格与项目权限。
- 写入前核实目标工作区、项目、对象和权限，展示带工作区来源的具体方案并确认授权；已有明确授权可沿用原范围。目标未确定先询问；无权限时拒绝该目标，不切到其他 workspace 重试同名对象或绕过限制。

## 工作项

- **标题**：动词开头，说清楚要做成什么，不超过 60 字。例：「修复登录页在 Safari 下白屏」，不写「登录问题」。
- **描述**（Markdown）：
  - 背景：为什么要做（一两句）
  - 要做的：可验证的条目，用 `- [ ]` 列出
  - 验收标准：怎样算完成
  - 相关链接：设计稿、PR、文档
- **优先级**：
  - `urgent`：线上故障或阻塞他人，当天处理
  - `high`：本周期必须完成
  - `medium`：本周期计划内（默认）
  - `low`：有空再做
  - `none`：未评估
- **负责人**：创建时不确定就留空，不要随意指派他人；“分配给我”传 `me`。
- **截止日期**：只有真实的外部期限才填，不要用截止日期表达优先级。

## 状态流转

Backlog（待规划）→ Todo（已排期）→ In Progress（进行中）→ In Review（评审中，如果项目有）→ Done（完成）/ Cancelled（取消）。

- 开始动手时改为“进行中”状态组（`started`）。
- 提了 PR 但未合并，保持进行中或评审中，不要提前改为完成。
- 只有“已完成”或“已取消”的工作项可以归档。

具体状态名以项目为准，先用 `project` 工具 `action="states", workspace_slug="<目标 slug>"` 查看。

## 分支与提交

- 分支名：`<type>/<工作项编号>-<简短英文描述>`，如 `fix/WEB-123-safari-login`；type 用 feat / fix / chore / refactor / docs。
- PR 标题以工作项编号开头：`[WEB-123] fix: ...`。

## 安全

- 删除、批量归档、批量修改之前，先列出将受影响的工作项并等待用户确认。
- 不要修改他人负责的工作项的负责人或截止日期，除非用户明确要求。

# plane-setup：连接 Plane

## 执行边界

先遵循 Plane 团队规范。没有可用 Plane MCP 时只草拟，不宣称读取或写入成功。调用参数以当前工具 schema 为准。

先调用 `workspace(action="list")` 定位目标；歧义时询问。除该发现调用外，每次读取、分页、写入及核验都显式传 `workspace_slug`，同时携带目标项目和对象标识。跨工作区分别查询、分别分页并标明 slug 与项目来源；不得使用历史默认工作区，不得在无权限时切换工作区重试同名对象。

列表按返回的 cursor、next_page 或 has_more 连续分页，直到结束；如果达到客户端预算、权限受限或某页失败，明确标注仅覆盖已读取范围，不把部分数据当作全量排名、计数或规划依据。不要猜测分页参数。

写入前展示具体目标与变更，获得用户明确确认；已有明确授权仅在原范围内沿用。沉默、空消息或回车不算确认。任何步骤失败立即停止依赖它的后续操作，报告已成功、失败和未执行部分；结果不明时先读取核验，避免重复创建。写后读取核验，只报告已证实的结果。

## 1. 检查连接

调用 `workspace(action="list")`，确定目标后调用 `workspace(action="me", workspace_slug="<目标 slug>")` 核验身份，再分页查询 `project(action="list", workspace_slug="<目标 slug>")`。展示身份、工作区 slug 和最多十个项目，并说明是否只展示部分。

没有 Plane 工具或返回 401 时指导下面的 OAuth 连接或手动配置；403 表示权限不足，停止该目标操作，不切区回退。只读令牌可查询，不能执行写入。

## 2. OpenAI 插件 OAuth 连接

OpenAI 插件包含绑定实例的 MCP 地址。用户在插件中点击连接，浏览器打开 Plane 登录与授权页，选择工作区和只读或读写权限，完成后返回客户端。没有连接入口时检查插件版本是否为 0.3.0 或更新、是否启用，以及是否需要新建会话；不要把安装技能等同于连接成功。

连接地址以当前插件的 mcp.json 为准，不从历史会话推断。其他部署需要从源码修改 instance.json 并重新构建插件；不能要求用户把 Token 放进聊天或通过 URL 参数传递。实例须部署 OAuth 后端，并通过 /.well-known/oauth-protected-resource 提供发现信息。连接失败时报告实际错误，不回退到无认证模式。

授权默认只读；需要修改数据时用户须显式勾选读写权限，并仍按每项技能的具体操作授权执行。用户可以在该实例个人设置 → 开发者 → MCP 中查看和撤销连接。授权过期、撤销或工作区成员资格失效后重新连接。

## 3. 保留 API Token 接入

1. 在 Plane「个人设置 → API 令牌」创建令牌，仅查询可选择只读。
2. 支持手动 MCP 配置的客户端可添加 Streamable HTTP URL：`https://plane.example.com/mcp`，认证请求头为 `Authorization: Bearer <Plane API token>`，或使用安全环境变量引用。
3. 保存并重新连接，再执行上述只读自检。客户端没有相应设置或不能发送所需请求头时，报告限制，不声称已连接。

不要把 API Token 填入 OAuth client secret。不要要求用户将令牌贴进对话、技能或仓库。只有只读自检成功后才能报告连接成功。

## 1. 取数据

1. `workitem` 工具 `action="my_summary", workspace_slug="<目标 slug>"`
2. `workitem` 工具 `action="my_items", workspace_slug="<目标 slug>"`，`filters={"state_group__in":"unstarted,started"}`
3. 明确用户时区和汇总区间（周一可从上周五算起），读取已完成工作项及必要的活动记录。只有 `completed_at` 或活动记录中的“进入 completed 状态”时间落在区间内，才能列为该时段完成。`updated_at` 只表示更新，不能作为完成时间证据；缺少完成时间证据时列为“近期更新的已完成项，完成时间待确认”，不计入昨天完成。

## 2. 汇总（Markdown）

```
## 站会 YYYY-MM-DD

**昨天完成**
- WEB-12 修复登录页白屏

**今天计划**
- WEB-30 导出报表加筛选（10/20 截止）

**风险 / 阻塞**
- WEB-8 已逾期 3 天：<原因，未知就写“待确认”>
```

- 今天计划最多 5 条，优先进行中和逾期的。
- 风险只写逾期、7 天内到期但未开始、urgent 未开始的工作项。
- 不要编造原因。

# issue-breakdown：拆需求

## 执行边界

先遵循 Plane 团队规范。没有可用 Plane MCP 时只草拟，不宣称读取或写入成功。调用参数以当前工具 schema 为准。

先调用 `workspace(action="list")` 定位目标；歧义时询问。除该发现调用外，每次读取、分页、写入及核验都显式传 `workspace_slug`，同时携带目标项目和对象标识。跨工作区分别查询、分别分页并标明 slug 与项目来源；不得使用历史默认工作区，不得在无权限时切换工作区重试同名对象。

列表按返回的 cursor、next_page 或 has_more 连续分页，直到结束；如果达到客户端预算、权限受限或某页失败，明确标注仅覆盖已读取范围，不把部分数据当作全量排名、计数或规划依据。不要猜测分页参数。

写入前展示具体目标与变更，获得用户明确确认；已有明确授权仅在原范围内沿用。沉默、空消息或回车不算确认。任何步骤失败立即停止依赖它的后续操作，报告已成功、失败和未执行部分；结果不明时先读取核验，避免重复创建。写后读取核验，只报告已证实的结果。

## 1. 输入

需求可能来自：

- 用户直接给的文字
- Plane 页面：`page` 工具 `action="get", workspace_slug="<目标 slug>"`
- 已有工作项：`workitem` 工具 `action="get", workspace_slug="<目标 slug>"`（拆成它的子工作项）

确定目标项目；不明确就问。用 `project` 工具 `action="labels", workspace_slug="<目标 slug>"` 和 `action="states", workspace_slug="<目标 slug>"` 了解可用的标签和状态。

## 2. 拆分方案（先不创建）

按 Plane 团队规范 的规范拟定：

- 一个父工作项（输入已是工作项时就用它）
- 3–10 个子工作项，每个半天到三天的工作量，能独立验收；每个写标题、一句话描述、建议优先级、建议标签

用表格展示，问：「按这个创建？可以增删改」。

## 3. 创建

确认后：

1. 需要时创建父工作项：`workitem` 工具 `action="create", workspace_slug="<目标 slug>"`，描述里写完整背景与验收标准。
2. 逐个创建子工作项，传 `parent=<父编号>`。
3. 如果用户要求，把它们加入周期（`cycle` 工具 `action="add_items", workspace_slug="<目标 slug>"`）或模块。

任何一步失败就停下，报告已创建的部分，不要重试到底。

## 4. 汇报

列出创建的编号与标题，以及父工作项编号。
